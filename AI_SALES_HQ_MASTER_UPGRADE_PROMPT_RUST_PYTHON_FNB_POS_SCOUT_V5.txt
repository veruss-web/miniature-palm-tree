Permintaan Rust + Hybrid Python adalah requirement inti, bukan opsi dan
bukan sekadar membuat file rust_backend.py placeholder.

3.1 Pembagian tanggung jawab

RUST CORE:
Gunakan Rust untuk komponen yang mendapat manfaat nyata dari performa,
konkurensi, keamanan memori, dan pemrosesan throughput tinggi:
- high-throughput ingestion normalization;
- canonicalization dan deduplication kandidat;
- feature extraction deterministik;
- scoring primitives yang murni dan terukur;
- event processing / batch transformation;
- text preprocessing yang tidak memerlukan LLM;
- queue/batch utilities jika benchmark membuktikan manfaat;
- data validation dan policy primitives yang cocok dipindahkan;
- komputasi berat lain berdasarkan profiling.

PYTHON CONTROL PLANE:
Pertahankan Python untuk:
- kernel/orchestration;
- agent workflow dan state machine;
- LLM provider dan prompt management;
- connector API eksternal;
- business logic yang cepat berubah;
- CRM, persistence, migrations;
- webhook/API server;
- analytics, dashboard backend;
- integration tests dan operational tooling.

Jangan memindahkan seluruh sistem ke Rust hanya demi label. Jangan pula
membiarkan Python tetap menjadi satu-satunya backend tanpa alasan.
Pilih boundary yang jelas dan ukur.

3.2 Implementasi teknis Rust
- Buat workspace Cargo yang terstruktur dan dapat dibangun.
- Buat crate library Rust dengan API stabil.
- Gunakan PyO3/maturin untuk binding Python jika kompatibel dengan target.
  Jika target Android/Termux tidak mendukung toolchain tertentu, evaluasi
  alternatif FFI/CLI/library dan dokumentasikan alasan teknis.
- Buat wrapper Python dengan feature detection dan fallback yang transparan.
- Jangan mengklaim Rust aktif bila modul native tidak berhasil dimuat.
- Buat parity test Python vs Rust untuk semua fungsi yang dipindahkan.
- Output harus identik atau memiliki toleransi numerik yang ditentukan.
- Tambahkan fuzz/property tests untuk parser, normalizer, dedup dan scoring.
- Tambahkan benchmark Python vs Rust dengan dataset representatif.
- Jangan mengaktifkan Rust hanya karena lebih cepat pada microbenchmark;
  ukur end-to-end latency, throughput, memory, startup, dan biaya kompleksitas.
- Rust build gagal tidak boleh membuat sistem kehilangan data atau
  menghasilkan output yang diam-diam berbeda.
- Catat backend yang digunakan per operasi dan fallback reason.

3.3 Definition of Done Rust
- Cargo build/test lulus.
- Python extension berhasil diimpor pada target yang dinyatakan didukung.
- Parity suite lulus.
- Benchmark dapat direproduksi.
- Fallback Python diuji.
- Status `rust_active`, `python_fallback`, `unavailable` ditampilkan jujur.
- Tidak ada placeholder `NOT_IMPLEMENTED` untuk scope Rust yang dijanjikan.

4. AI / LLM PROVIDER DAN KECERDASAN AGENT
======================================================================

4.1 Provider
Selesaikan integrasi nyata:
- Google Gemini melalui API resmi.
- Ollama lokal melalui API resmi untuk model yang sudah terpasang.
- Provider interface generik agar provider tambahan dapat dipasang kemudian.
- Mock provider hanya untuk test; tidak boleh disalahartikan sebagai AI nyata.
- Health check, timeout, retry terkontrol, exponential backoff, quota handling,
  rate-limit handling, circuit breaker, telemetry, dan provider fallback.
- Validasi API key dan model tanpa menampilkan secret.
- Jangan mengunduh model Ollama otomatis tanpa konfigurasi eksplisit.
- Provider harus dapat diuji dengan koneksi nyata jika jaringan dan kredensial
  tersedia; bila tidak, tandai NOT_VERIFIED dan sediakan langkah verifikasi.

4.2 Model routing
Rancang model routing berdasarkan tugas, bukan satu model untuk semua:
- intent classification;
- entity extraction;
- prospect research synthesis;
- lead qualification;
- conversation response;
- objection handling;
- proposal drafting;
- quality critique;
- summarization.
Gunakan model lebih ringan untuk tugas sederhana dan model lebih kuat untuk
tugas yang membutuhkan reasoning. Pertimbangkan latency, biaya, privasi,
context window, structured output, dan availability.

4.3 LLM safety and correctness
- Gunakan JSON schema / structured output bila tersedia.
- Parse dan validate semua output LLM.
- LLM tidak boleh mengubah state database secara langsung.
- LLM hanya mengusulkan tindakan; kernel dan GUARDIAN memvalidasi.
- Tool calling menggunakan allowlist, schema, timeout, budget, dan audit.
- Prompt injection dari website, email, pesan pelanggan, dokumen, dan hasil
  pencarian diperlakukan sebagai untrusted data.
- Pisahkan system instruction dari konten eksternal.
- Jangan masukkan API key, credential, private customer data, atau data
  sensitif yang tidak dibutuhkan ke prompt.
- Tambahkan grounded response: klaim harus menunjuk catalog/evidence/quote.
- Confidence rendah atau konflik data → bertanya, menahan klaim, atau handover.
- Evaluasi kualitas model per tugas, bukan hanya jawaban terlihat bagus.

4.4 Agent roles

SCOUT:
- Source discovery, query planning, ingestion, normalization, entity resolution,
  business classification, contact discovery yang sah, website footprint,
  technology/commerce signals, evidence capture, freshness, dedup.
- Menghasilkan lead record dan evidence; tidak mengirim pesan.

ANALYST:
- Menggabungkan bukti SCOUT dengan kebutuhan bisnis.
- Menilai website need, e-commerce need, POS need, integration need.
- Menilai fit produk, urgency, budget signals jika sah dan tersedia,
  decision-maker confidence, timing, risk, data confidence.
- Menghasilkan score yang explainable, bukan angka misterius.
- Menentukan next-best-action dan alasan prioritas.
- Consent bukan komponen skor; izin adalah gerbang kelayakan kontak.

CLOSER:
- Conversation state dan memory per customer.
- Intent multi-label dan entity extraction.
- Discovery question planning.
- Personalized opening, product explanation, demo scheduling,
  objection handling, proposal, negotiation, follow-up dan handover.
- Menggunakan katalog aktual, quote engine, demo registry dan action registry.
- Tidak membuat janji yang tidak didukung.
- Menyimpan ringkasan memori dengan provenance dan correction handling.
- Hanya satu agent pemilik percakapan pada satu waktu.

GUARDIAN:
- Deterministic policy enforcement dan veto.
- Consent, lawful basis, suppression, opt-out, contact lock, rate limit,
  quiet hours, channel policy, approval, message lint, claim lint,
  privacy, security, budget, kill switch, audit.
- Memeriksa setiap outbound message dan tool action.
- Tidak dapat di-bypass oleh LLM, admin biasa, agent lain, retry, atau fallback.
- Hard block harus menang atas business objective.

5. SCOUT: DEEP F&B DISCOVERY — POS MAKANAN & MINUMAN
======================================================================

MISI SCOUT
SCOUT adalah mesin prospect intelligence yang menemukan bisnis F&B yang
mungkin membutuhkan sistem kasir/POS. Ia mencari dari bukti publik yang sah,
memisahkan fakta dari dugaan, menilai kecocokan produk, dan menyerahkan
prospek yang dapat diverifikasi kepada ANALYST. SCOUT tidak mengirim pesan,
tidak mengarang pain point, dan tidak menganggap semua bisnis F&B butuh POS.

5.1 HIERARKI TARGET DAN SEGMENTASI

TIER 1 — F&B DENGAN POTENSI KEBUTUHAN POS TINGGI:
- restoran, rumah makan, warung makan, dan kedai;
- cafe, coffee shop, tea shop, bubble tea, juice bar, dan gerai minuman;
- food stall, gerai take-away, food court tenant, dan gerai cepat saji;
- bakery, toko roti, toko kue, dessert shop, snack, dan jajanan;
- katering, cloud kitchen, central kitchen, dan dapur produksi;
- franchise kuliner dan bisnis multi-outlet;
- frozen food dan toko pangan dengan variasi produk serta transaksi kasir.

TIER 1A — SUBSEGMEN KHUSUS YANG TETAP DIPERTAHANKAN:
- pabrik/produsen es tube dan es kristal;
- distributor, agen, sub-agen, grosir, supplier, depot, dan toko es;
- supplier es untuk cafe, restoran, hotel, katering, dan pedagang minuman.
Subsegmen ini adalah bagian dari target F&B/food supply, bukan batas tunggal
seluruh pencarian.

TIER 2 — F&B BERBASIS PRODUKSI/DISTRIBUSI:
- produsen makanan/minuman dengan penjualan langsung atau counter sales;
- distributor makanan/minuman yang mempunyai transaksi penjualan langsung;
- supplier bahan baku F&B jika ada kebutuhan POS yang jelas;
- toko daging/seafood/bahan pangan jika alur kasir dan stok cocok.

TIER 3 — TARGET SEKUNDER DEFAULT OFF:
- retail non-makanan, fashion, elektronik, jasa, dan sektor lain.
Hanya dicari bila owner mengaktifkan secara eksplisit. Jangan mencampurkan
hasil Tier 3 dengan prioritas F&B.

Segmentasikan berdasarkan tipe usaha, model transaksi, channel penjualan,
jumlah outlet yang terverifikasi, kompleksitas menu/produk, dan bukti
kebutuhan POS. Simpan segment_code, tier, business_model, geography,
source provenance, dan alasan klasifikasi.

5.2 QUERY INTELLIGENCE BAHASA INDONESIA

Query planner harus menggabungkan kata kunci jenis usaha, kebutuhan POS,
dan geografi. Contoh query F&B:
- "restoran", "rumah makan", "warung makan", "kedai makan";
- "cafe", "coffee shop", "kedai kopi", "tea shop", "bubble tea",
  "juice bar", "kedai minuman";
- "bakery", "toko roti", "toko kue", "dessert", "snack", "jajanan";
- "katering", "catering", "cloud kitchen", "dapur produksi";
- "food stall", "take away", "gerai makanan", "food court";
- "franchise makanan", "cabang restoran", "jaringan cafe";
- "frozen food", "toko frozen", "toko daging", "supplier bahan makanan".

Query khusus es:
- "pabrik es tube", "produsen es kristal", "distributor es tube",
  "agen es kristal", "grosir es tube", "depot es kristal",
  "supplier es untuk cafe/restoran".

Query berbasis kebutuhan POS:
- "butuh aplikasi kasir", "software kasir", "sistem POS",
  "aplikasi stok toko", "lowongan kasir", "admin penjualan",
  "pencatatan penjualan manual", "rekap penjualan", "sistem kasir restoran".
Gunakan hanya query yang tidak melanggar kebijakan sumber dan jangan
menganggap hasil kata kunci sebagai bukti final.

Gabungkan query dengan kota/kabupaten/kecamatan yang dipilih operator.
Gunakan synonym dictionary dan variasi lokal yang dapat dikonfigurasi.
Catat query asal, query turunan, wilayah, sumber, jumlah hasil, deduplikasi,
yield prospek, dan kualitas lead. Sediakan coverage map/table, checkpoint,
resume, budget/quota, dan stop conditions. Jangan mencari tanpa batas.

5.3 SUMBER DATA DAN LEGALITAS

Sumber yang boleh digunakan:
- Google Places API / Google Maps Platform sesuai ketentuan resmi dan quota;
- website bisnis publik dengan crawler terbatas, robots.txt, terms,
  rate limit, timeout, batas ukuran, dan SSRF protection;
- akun/halaman sosial bisnis melalui API resmi dan permission yang sesuai;
- direktori bisnis yang memiliki lisensi/izin penggunaan jelas;
- daftar bisnis/CSV yang diberikan owner;
- sumber publik lain setelah legal basis dan terms dinilai.

Dilarang bypass login/CAPTCHA/paywall/rate limit/access control, scrape
profil privat/pesan privat/grup tertutup, membuat akun palsu, memakai
endpoint tidak resmi lalu mengklaim resmi, atau mengambil data personal
tanpa dasar yang sah. Jangan mengirim DM/WhatsApp/email/telepon pada tahap
discovery. Data publik tidak otomatis boleh dipakai untuk semua pemasaran.

Setiap connector wajib memiliki credential validation, health check,
capability declaration, quota/rate limit, pagination/resume, retry/backoff,
source provenance, terms metadata, data minimization, contract tests, dan
status LIVE_VERIFIED / SANDBOX_VERIFIED / MOCK_ONLY / NOT_CONFIGURED /
BLOCKED_EXTERNAL. Jangan pernah memalsukan hasil live.

5.4 SIGNAL INTELLIGENCE — BUKTI KEBUTUHAN POS

Pisahkan sinyal menjadi kategori:

A. IDENTITAS F&B:
- bisnis benar-benar menjual/menyajikan makanan atau minuman;
- tipe usaha (restoran, cafe, warung, bakery, katering, dan sebagainya);
- lokasi/outlet dan area layanan yang dinyatakan;
- model dine-in/take-away/delivery jika terlihat;
- menu/katalog publik dan variasi produk;
- kontak bisnis resmi.

B. KOMPLEKSITAS TRANSAKSI:
- banyak menu/SKU atau varian;
- antrean/transaksi cepat;
- dine-in dan take-away;
- banyak kasir/shift;
- banyak outlet/cabang yang terverifikasi;
- order dari beberapa kanal;
- transaksi grosir dan eceran;
- pelanggan tetap atau B2B;
- stok barang jadi atau bahan baku yang relevan.

C. PAIN SIGNAL POS:
- bisnis secara eksplisit menyebut pencatatan manual/buku/spreadsheet;
- pemilik secara eksplisit mencari aplikasi kasir/POS;
- lowongan kasir/admin menyebut tugas rekap transaksi manual;
- bisnis menyatakan kesulitan mengontrol stok, penjualan, atau laporan;
- ekspansi outlet dapat menjadi sinyal kompleksitas, bukan bukti POS gagal;
- review publik yang relevan tentang salah catat/antrean/rekap hanya
  boleh menjadi petunjuk, dengan konteks dan sumber yang jelas.

D. DIGITAL/ORDER SIGNAL:
- order melalui WhatsApp/telepon/media sosial;
- tidak ada checkout online;
- menu hanya berupa gambar/posting;
- tidak terlihat katalog online.
Semua ini hanya sinyal POSSIBLE. Order lewat chat bukan bukti bahwa kasir
atau pencatatan internal buruk. Tidak memiliki website bukan bukti butuh POS.
Memiliki website/checkout bukan bukti sudah memiliki POS.

E. SUBSEGMEN ES:
- bukti benar-benar memproduksi/menjual/distribusi es tube/kristal;
- transaksi eceran/partai;
- kemasan/satuan yang terlihat;
- pelanggan bisnis berulang;
- kebutuhan stok/pengiriman yang dinyatakan.
Jangan menyamakan restoran yang membeli es dengan distributor es.

5.5 WEBSITE DAN DIGITAL FOOTPRINT INTELLIGENCE

Periksa website publik secara ringan:
- status dan identitas bisnis;
- menu/katalog dan informasi order;
- kanal order, pembayaran, pengiriman;
- jumlah outlet yang dinyatakan;
- kontak bisnis resmi;
- indikator teknologi yang dapat diamati secara wajar;
- basic status HTTP, redirect, TLS, responsive hints, dan broken links.

Jangan mengirim form, membuat akun, melakukan order, mencoba pembayaran,
atau menjalankan security scan agresif. Ketiadaan fitur digital bukan bukti
bahwa POS internal tidak ada.

5.6 EVIDENCE LEDGER DAN PROVENANCE

Setiap sinyal disimpan terpisah:
lead_id, business_entity_id, source_id, source_type, source_url/reference,
observed_at, collected_at, evidence_type, excerpt minimum/hash bila aman,
OBSERVED/INFERRED/UNKNOWN/CONFLICTED/STALE, confidence, freshness,
review status, policy/terms metadata, expiry/recheck_after.

Bedakan fakta yang terlihat langsung dari dugaan. Setiap skor harus
ditelusuri ke evidence ID. Jangan simpan PII atau halaman penuh tanpa
kebutuhan dan dasar yang sah. Sediakan evidence viewer dengan kutipan
minimum, tautan sumber, tanggal, dan alasan skor.

5.7 ENTITY RESOLUTION DAN DEDUP

Gunakan nama ternormalisasi, domain, alamat, koordinat dari sumber sah,
kontak bisnis publik, brand/alias, dan relasi outlet. Jangan auto-merge
hanya karena nama mirip. Bedakan kantor pusat, outlet, cabang, dapur pusat,
gudang, dan agen bila evidence mendukung. Simpan merge history dan undo.

5.8 SCOUT SCORE — TIGA DIMENSI TERPISAH

A. F&B NICHE FIT (0–100):
Apakah entitas benar-benar bisnis makanan/minuman atau rantai pasok F&B?
Untuk es, apakah benar produsen/distributor/agen/depot/toko es?

B. POS NEED EVIDENCE (0–100):
Apakah ada bukti eksplisit kebutuhan kasir, transaksi, stok, pelanggan,
shift, laporan, atau pengelolaan outlet? Jangan beri nilai seolah terbukti
untuk faktor yang UNKNOWN.

C. MIEFLOW PRODUCT CAPABILITY FIT (0–100):
Apakah fitur MIEFLOW yang sudah diverifikasi cocok dengan kebutuhan?
Periksa MUST_HAVE dan product gaps. Kebutuhan kritis yang belum didukung
menghasilkan PRODUCT_GAP_BLOCKER.

Status akhir:
- HIGH_PRIORITY: niche fit, POS evidence, dan capability fit kuat; evidence
  fresh; tidak ada blocker kritis.
- QUALIFY: niche fit kuat, tetapi kebutuhan POS perlu diverifikasi.
- NICHE_ONLY_NO_POS_EVIDENCE: F&B fit tetapi bukti kebutuhan POS belum cukup.
- POS_NEED_OUTSIDE_FNB: kebutuhan POS terindikasi tetapi bukan F&B; hanya
  diproses jika owner mengaktifkan sektor sekunder.
- PRODUCT_GAP_BLOCKER: kebutuhan utama tidak didukung MIEFLOW saat ini.
- NOT_A_FIT / UNKNOWN / CONFLICTED / STALE.

Jangan membuat satu skor misterius. Tampilkan dimensi, evidence IDs,
missing facts, confidence, freshness, dan alasan keputusan.

5.9 QUERY LEARNING DAN FEEDBACK LOOP

Belajar dari label operator:
CORRECT_FNB_SEGMENT, WRONG_BUSINESS_TYPE, POS_NEED_CONFIRMED,
POS_NEED_NOT_PROVEN, PRODUCT_GAP, DUPLICATE, STALE, CONTACT_NOT_ELIGIBLE,
QUALIFIED, REJECTED. Versioning query, synonym, threshold, bobot, dan model.
Jangan biarkan feedback mengubah hard safety rules. Jangan gunakan data
pelanggan untuk training eksternal tanpa izin.

5.10 HANDOFF SCOUT → ANALYST

Handoff memuat business profile, F&B segment/tier, bukti produk/layanan,
POS need evidence, F&B niche score, POS need score, capability fit,
missing facts, source references, confidence, freshness, contact eligibility,
dan pertanyaan discovery yang disarankan.

SCOUT tidak boleh mengirim pesan, mengarang budget/omzet/volume/karyawan/
jumlah cabang/decision-maker/teknologi, atau mengirim lead ke CLOSER tanpa
qualification ANALYST. Hormati opt-out dan suppression list.

5.11 CONNECTOR OBSERVABILITY DAN JOB CONTROL

Tampilkan query/wilayah, segmen F&B, sumber aktif, hasil mentah/valid/
duplikat/ditolak, quota/biaya, retry/error/checkpoint, evidence per kategori,
jumlah NICHE_ONLY_NO_POS_EVIDENCE, lead ke ANALYST, durasi dan throughput.
Dashboard mendukung pause/resume/cancel/retry/export sesuai hak akses.
Tandai connector MOCK_ONLY atau NOT_CONFIGURED dengan jelas.

5.12 ACCEPTANCE TEST SCOUT

Minimal tests:
1. Restoran dengan bukti menu dan outlet → F&B niche fit.
2. Cafe/coffee shop dengan menu dan kontak bisnis publik → F&B niche fit.
3. Warung makan kecil tanpa bukti POS → niche fit, POS need unknown.
4. Bisnis secara eksplisit mencari aplikasi kasir → POS evidence kuat.
5. Order via WhatsApp saja → POSSIBLE, bukan confirmed manual pain.
6. Tidak punya website → bukan bukti butuh POS.
7. Punya checkout online → bukan bukti punya/tidak punya POS internal.
8. Franchise dengan cabang yang terbukti → entity relationship benar.
9. Bakery/katering/cloud kitchen → segmen F&B sesuai evidence.
10. Pabrik es tube/distributor es → segmen khusus es, tetap termasuk target.
11. Restoran yang hanya membeli es → bukan distributor es.
12. Retail fashion tanpa sektor sekunder aktif → bukan target.
13. Data lama → STALE; sumber bertentangan → CONFLICTED.
14. Sumber MOCK_ONLY → tidak boleh disebut live.
15. Kebutuhan kitchen printer/table management/recipe costing yang belum
    didukung → PRODUCT_GAP_BLOCKER.
16. Kebutuhan piutang/satuan kg/harga grosir yang belum didukung → GAP.
17. Prospek opted-out/contact-ineligible → tidak boleh outbound.
18. Dua bisnis bernama mirip tetapi berbeda → jangan auto-merge.
19. Query terlalu umum tanpa kata F&B/geografi → tidak boleh menghasilkan
    klaim target berkualitas.
20. Hasil pencarian tanpa bukti identitas F&B → UNKNOWN/REJECTED.

6. ANALYST: QUALIFICATION DAN PRIORITAS
======================================================================

Buat model penilaian yang explainable dan configurable. Pisahkan:
A. Product fit:
- POS / sistem kasir fit saja.
- Niche fit untuk usaha es tube/es kristal.
- Capability fit terhadap fitur POS yang benar-benar tersedia.
E-commerce, website fit, dan paket gabungan bukan kategori produk penjualan.
B. Need strength:
- pain point yang terbukti;
- proses manual;
- kompleksitas katalog/order;
- jumlah cabang bila tersedia;
- sinyal ekspansi;
- masalah transaksi, stok, pencatatan, atau laporan yang teramati;
- relevansi solusi.
C. Buying readiness:
- minat eksplisit;
- waktu kebutuhan;
- decision-maker evidence;
- permintaan demo/penawaran;
- budget hanya jika disampaikan atau tersedia secara sah.
D. Evidence confidence:
- sumber independen;
- freshness;
- direct vs inferred;
- conflict.
E. Contact eligibility:
- consent, lawful basis, channel policy, suppression, opt-out.
Contact eligibility bukan skor probabilitas dan tidak dapat di-override oleh nilai
lead yang tinggi.

Output:
- score per product;
- overall priority;
- confidence;
- rationale;
- supporting evidence;
- missing information;
- disqualification reason;
- next-best-action;
- review_required.
Rubrik dan bobot harus dapat dikonfigurasi, diberi versi, dan diuji. Jangan
menganggap bobot awal proyek sebagai kebenaran ilmiah. Kalibrasikan dengan
data hasil penjualan nyata dan hindari bias kategori/ukuran bisnis.

7. CLOSER: AI SALES CONVERSATION YANG BENAR-BENAR BEKERJA
======================================================================

CLOSER harus berkembang dari draft-only menjadi conversation agent yang
dapat menjalankan percakapan nyata melalui channel connector yang sah.

7.1 Conversation engine
- Webhook inbound event dengan signature verification.
- Idempotency untuk mencegah pesan ganda.
- Ordering dan dedup event.
- Conversation ownership lock.
- Customer identity resolution dengan batas privasi.
- Context window management dan memory summarization.
- Per-customer CRM timeline.
- Intent/entity extraction.
- Language detection dan tone adaptation.
- Human handover.
- Delivery/read/reply status bila provider mendukung.
- Retry aman tanpa mengirim pesan ganda.
- Dead-letter queue dan replay yang diaudit.

7.2 Natural sales behavior
AI harus dapat:
- memperkenalkan solusi secara singkat dan relevan;
- menggali kondisi bisnis;
- memahami apakah pelanggan membutuhkan E-commerce/toko online, POS/kasir,
  atau kombinasi keduanya;
- bertanya satu pertanyaan paling penting per giliran;
- menyesuaikan penjelasan dengan industri pelanggan;
- memberi contoh alur kerja yang relevan;
- menjelaskan manfaat tanpa menjamin hasil finansial;
- membandingkan pilihan paket dari katalog;
- menjawab keberatan harga, waktu, kompleksitas, kepercayaan, migrasi,
  dukungan, integrasi, dan kesiapan tim;
- menawarkan demo;
- menyusun proposal dan quotation;
- melakukan negosiasi dalam rentang diskon dan syarat yang diizinkan;
- mencatat alasan kalah/menang;
- melakukan follow-up hanya bila memiliki dasar izin dan aturan kanal
  memperbolehkan;
- berhenti segera jika pelanggan menolak/opt-out.

7.3 Sales knowledge base
Buat sumber kebenaran terstruktur:
- product catalog;
- feature matrix;
- package/pricing;
- implementation timeline;
- onboarding process;
- support/SLA;
- integration compatibility;
- security/privacy statements;
- FAQ;
- case studies/testimonials yang terverifikasi;
- demo assets;
- terms and limitations.
Setiap item punya version, owner, last_verified_at, status, evidence.
AI dilarang mengarang jawaban jika knowledge base kosong. Jawab jujur,
ajukan klarifikasi, atau handover.

7.4 Objection playbook
Bangun playbook yang dapat dikonfigurasi dan dievaluasi untuk:
- "mahal";
- "saya sudah punya website/POS";
- "belum butuh";
- "takut sulit digunakan";
- "takut data hilang";
- "apakah bisa integrasi dengan ...?";
- "bisa bayar bertahap?";
- "saya perlu diskusi dengan partner";
- "kirim proposal dulu";
- "apa bedanya dengan kompetitor?";
- "berapa lama pengerjaannya?".
Jangan memaksa, menekan, memanipulasi, membuat scarcity palsu, atau
menggunakan dark patterns.

7.5 Pricing and negotiation
- Semua harga berasal dari katalog/quote engine yang disetujui pemilik.
- Harga final, diskon, pajak, biaya tambahan, masa berlaku, dan syarat
  harus dihitung deterministik.
- Batas diskon per role/agent.
- AI tidak boleh memberi diskon atau komitmen di luar kewenangannya.
- Untuk permintaan khusus, buat approval task atau handover.
- Quote memiliki ID, versi, expiry, itemized lines, currency, tax treatment,
  dan audit trail.

7.6 Deal and payment
- Status deal tidak boleh WON hanya karena pelanggan berkata "oke".
- Verifikasi pembayaran melalui payment provider/webhook resmi atau bukti
  yang diverifikasi manusia.
- Jangan menyimpan data kartu pembayaran.
- Idempotency dan reconciliation.
- Simpan bukti minimum yang diperlukan.
- Setelah deal valid, buat onboarding handoff dan task implementasi.

8. CHANNELS: INBOUND DAN OUTBOUND NYATA
======================================================================

Buat channel architecture modular:
- WhatsApp Business Platform / Cloud API resmi jika memenuhi syarat.
- Email melalui provider resmi (SMTP/API) dengan autentikasi yang benar.
- Website live chat/widget.
- Instagram/Messenger hanya melalui API dan permission resmi yang tersedia.
- Channel tambahan melalui connector contract.

Khusus WhatsApp:
- Gunakan WhatsApp Business Platform/Cloud API resmi.
- Implementasikan webhook verification, signature, message status, template
  messages, 24-hour customer service window, template category, opt-in,
  quality rating/rate limits sesuai dokumentasi terkini.
- Jangan menggunakan WhatsApp Web automation, browser bot, unofficial library,
  atau teknik yang menghindari aturan.
- Jangan mengirim cold message tanpa dasar izin yang sesuai.
- Inbound customer-initiated conversation dapat ditangani sesuai window
  dan policy resmi.
- Jika outbound business-initiated memerlukan template/opt-in, patuhi.
- Sediakan sandbox/test number bila tersedia.

Email:
- SPF/DKIM/DMARC guidance.
- Bounce, complaint, unsubscribe, suppression.
- Rate limit dan sender reputation.
- Tidak melakukan spam/bulk cold email yang melanggar hukum atau provider policy.

Website chat:
- Widget ringan, secure session, rate limiting, consent notice, privacy notice.
- Handover ke manusia.
- Tidak mengungkap data pelanggan lain.

Sender Gateway:
- Semua outbound wajib melewati satu jalur GUARDIAN authorize_send.
- Adapter hanya dapat diregistrasi bila official/approved.
- Default deny.
- Idempotency key per outbound.
- Delivery uncertain tidak boleh auto-resend tanpa reconciliation.
- Per-channel kill switch dan global kill switch.
- Per-customer contact lock dan suppression lintas kanal.
- Audit setiap keputusan allow/deny.
- Dry-run/sandbox/live mode yang jelas dan terpisah.

PENTING: Jangan mengaktifkan live outbound secara default. Implementasikan
fitur lengkap dan sandbox tests, tetapi konfigurasi awal tetap:
RESEARCH_ONLY=true
OUTBOUND_ENABLED=false
DRY_RUN=true
LIVE_SEND_APPROVED=false
GLOBAL_KILL_SWITCH=true
Sampai pemilik mengisi credential, menyelesaikan setup resmi, memastikan
consent dan kebijakan, dan secara eksplisit mengaktifkan kanal. Ini bukan
alasan untuk tidak membangun adapter; adapter dan seluruh tesnya tetap wajib.

10A.6. CARA AGENT MENGGUNAKAN KATALOG

SCOUT:
- Menemukan prospek dan menyimpan evidence kebutuhan.
- Menggunakan kategori/vertical dan indikator kebutuhan dari katalog
  untuk membantu query planning.
- Tidak boleh mengirim penawaran dan tidak boleh mengarang bahwa bisnis
  membutuhkan jasa tertentu.

ANALYST:
- Membandingkan kebutuhan prospek dengan jasa/paket POS published saja.
- Menghasilkan product-fit score per jasa beserta evidence, confidence,
  alasan cocok/tidak cocok, gap, dan pertanyaan discovery.
- Mengabaikan produk draft, archived, stale, atau unavailable.
- Tidak menjadikan harga murah sebagai satu-satunya alasan kecocokan.

CLOSER:
- Mengambil informasi hanya dari katalog/knowledge center versi aktif.
- Menjelaskan manfaat sesuai masalah yang telah dikonfirmasi.
- Mengajukan pertanyaan discovery jika data kebutuhan belum cukup.
- Menawarkan maksimal opsi yang relevan, bukan membanjiri calon pelanggan.
- Menjawab harga sesuai pricing_model.
- Membuat quote hanya melalui quote engine.
- Tidak menjanjikan fitur, timeline, diskon, hasil bisnis, atau SLA
  di luar data dan kewenangannya.
- Jika jawaban tidak ada di knowledge center, menyatakan belum memiliki
  informasi terverifikasi dan menawarkan handover.

GUARDIAN:
- Memvalidasi status publish, freshness, harga, diskon, klaim, bukti,
  izin penggunaan portofolio/testimoni, serta kewenangan agent.
- Memblokir penawaran dari produk draft/archived/stale.
- Memblokir diskon di luar batas.
- Memblokir klaim yang tidak punya evidence.
- Mencatat versi katalog dan knowledge base yang dipakai pada setiap
  percakapan, quote, dan proposal.

10A.7. PRICING ENGINE DAN QUOTE GENERATOR

Dukung tiga mode utama:
A. Fixed price: AI hanya menyampaikan harga yang ditetapkan.
B. Flexible within limits: AI dapat menyusun penawaran dalam rentang
   harga/diskon yang disetujui admin, dengan perhitungan transparan.
C. Custom quote after discovery: AI mengumpulkan kebutuhan dan membuat
   draft perhitungan; quote final harus mengikuti otorisasi yang ditetapkan.

Pilihan awal konfigurasi yang disarankan: flexible within limits.
Pilihan ini bukan harga otomatis dan tidak boleh membuat angka sendiri.
Jika admin belum memasukkan nilai batas harga/diskon, fleksibilitas
dinonaktifkan sampai aturan lengkap.

Quote engine wajib:
- menghitung subtotal, add-on, biaya setup, recurring fee, pajak/biaya,
  diskon, total, termin, dan masa berlaku;
- menyimpan input dan rumus perhitungan;
- mendukung versi quote dan revisi;
- mencatat siapa/agent yang membuat dan menyetujui;
- mencegah diskon bertumpuk yang melampaui batas;
- mengunci snapshot harga dan spesifikasi pada saat quote diterbitkan;
- menandai quote kedaluwarsa;
- tidak mengubah quote lama saat katalog berubah;
- mengharuskan handover jika harga custom memerlukan keputusan manusia.

10A.8. STATUS, PUBLIKASI, DAN PERUBAHAN KATALOG

Gunakan alur:
DRAFT → VALIDATION → PUBLISHED → STALE / ARCHIVED.

Ketentuan:
- hanya role berwenang dapat publish;
- perubahan besar pada harga/fitur membuat versi baru;
- quote yang sudah diterbitkan tetap memakai snapshot versi lama;
- perubahan katalog tidak boleh mengubah isi proposal historis;
- data yang melewati stale_after ditandai stale dan tidak boleh dipakai
  untuk klaim sensitif sampai diverifikasi ulang;
- setiap perubahan masuk audit log;
- sediakan preview sebelum publish dan rollback ke versi terdahulu;
- admin dapat menonaktifkan jasa segera jika ada kesalahan.

9. Diskon di luar batas ditolak GUARDIAN.
10. Quote lama mempertahankan snapshot versi saat dibuat.
11. Import CSV invalid tidak merusak katalog.
12. Admin dapat memulihkan versi katalog sebelumnya.
13. Hak akses mencegah user tanpa izin mengubah harga/publish.
14. Audit log mencatat perubahan, publikasi, arsip, dan rollback.
15. AI dapat menjawab "layanan apa saja yang tersedia?" hanya dari
    katalog published dan menjelaskan jika data belum lengkap.

Definition of Done:
Admin non-teknis dapat menambahkan satu jasa, paket, harga, fitur,
portofolio, FAQ, dan aturan penawaran melalui dashboard; menerbitkannya;
kemudian menjalankan simulasi percakapan dan membuktikan CLOSER

19. DEFINITION OF DONE GLOBAL
======================================================================

Proyek hanya boleh dinyatakan UPGRADED bila:

1. Fitur lama tetap bekerja atau perubahan breaking dijelaskan dan dimigrasikan.
2. Rust benar-benar dibangun, dipanggil dari Python untuk scope yang dipilih,
   parity-tested, benchmarked, dan fallback terlihat.
3. Gemini/Ollama memiliki integrasi implementasi nyata dan status verifikasi
   yang jujur.
4. SCOUT mendukung vertical bisnis penjual produk yang relevan untuk E-commerce/POS, bukan pencarian umum semua jenis usaha.
5. Ada connector source nyata yang sah dan dapat diverifikasi; connector lain
   yang memerlukan akses khusus diberi status NOT_CONFIGURED/NOT_VERIFIED.
6. ANALYST dapat menilai kebutuhan website/e-commerce/POS secara terpisah
   dan menjelaskan bukti.
7. CLOSER mampu multi-turn conversation menggunakan LLM dan knowledge base,
   bukan hanya draft deterministik.
8. Inbound channel nyata/sandbox berjalan dengan webhook dan idempotency.
9. Outbound adapter resmi tersedia dan melewati GUARDIAN authorize_send.
10. Consent, opt-out, contact lock, kill switch, rate limits, dan audit tidak
    dapat dilewati.
11. CRM dan dashboard tersedia serta responsif.
12. Quote, proposal, deal, payment verification, dan onboarding workflow ada.
13. Privacy export/delete dan retention berjalan serta diuji.
14. Semua unit/integration/e2e/adversarial tests dilaporkan.
15. Tidak ada klaim fitur, harga, konektor, atau status yang palsu.
16. Setup dan deployment terdokumentasi.
17. Semua known gaps ditampilkan dalam PRODUCTION_READINESS.md.

Jika satu syarat eksternal terhalang oleh credential, akses, biaya, approval,
atau policy pihak ketiga, jangan menyembunyikannya. Selesaikan implementasi
yang dapat dilakukan, sediakan sandbox, tulis langkah konfigurasi, dan
tandai status yang benar. Tidak boleh memalsukan live verification.

26. V5 F&B SEGMENT PRIORITY AND DISCOVERY PRINCIPLES
======================================================================

Prioritas discovery:
1. F&B dengan banyak transaksi/menu, antrean, beberapa kanal order, shift,
   stok, atau lebih dari satu outlet yang didukung evidence.
2. F&B yang secara eksplisit mengungkap kebutuhan kasir, stok, laporan,
   atau pencatatan penjualan.
3. Produsen/distributor/agen es tube dan es kristal dengan bukti transaksi
   kasir/penjualan dan kebutuhan POS.
4. F&B kecil tetap boleh ditemukan, tetapi jangan diberi prioritas tinggi
   tanpa evidence kebutuhan dan kecocokan produk.

Jangan bias hanya ke bisnis besar. Usaha kecil dapat cocok bila kebutuhan
dan fitur POS sesuai. Sebaliknya, restoran besar dapat tidak cocok bila
membutuhkan kitchen workflow, recipe costing, table management, integrasi
delivery, atau multi-outlet yang belum didukung.

SCOUT harus menyediakan filter dashboard:
- F&B segment;
- restaurant / warung / cafe / beverage / bakery / catering / cloud kitchen /
  food stall / franchise / frozen food / food supplier / ice supplier;
- city/region;
- niche fit;
- POS need evidence;
- product capability fit;
- product gap;
- evidence freshness;
- source status;
- qualification status.

Keluaran yang baik bukan "semua restoran di satu kota", tetapi daftar
prospek yang identitas F&B-nya terbukti, sinyal kebutuhan POS-nya jelas,
dan kebutuhannya cocok dengan fitur MIEFLOW yang benar-benar tersedia.
