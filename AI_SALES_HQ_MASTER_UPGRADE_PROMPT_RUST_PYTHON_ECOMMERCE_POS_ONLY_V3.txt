3. ARSITEKTUR RUST + PYTHON HYBRID — WAJIB DIIMPLEMENTASIKAN
======================================================================

Permintaan Rust + Hybrid Python adalah requirement inti, bukan opsi dan
bukan sekadar membuat file rust_backend.py placeholder.

3.1 Pembagian tanggung jawab

RUST CORE:
Gunakan Rust untuk komponen yang mendapat manfaat nyata dari performa,
konkurensi, keamanan memori, dan pemrosesan throughput tinggi:
- high-throughput ingestion normalization;
- canonicalization dan deduplication kandidat;
- feature extraction deterministik;
- scoring primitives yang murni dan terukur;
- event processing / batch transformation;
- text preprocessing yang tidak memerlukan LLM;
- queue/batch utilities jika benchmark membuktikan manfaat;
- data validation dan policy primitives yang cocok dipindahkan;
- komputasi berat lain berdasarkan profiling.

PYTHON CONTROL PLANE:
Pertahankan Python untuk:
- kernel/orchestration;
- agent workflow dan state machine;
- LLM provider dan prompt management;
- connector API eksternal;
- business logic yang cepat berubah;
- CRM, persistence, migrations;
- webhook/API server;
- analytics, dashboard backend;
- integration tests dan operational tooling.

Jangan memindahkan seluruh sistem ke Rust hanya demi label. Jangan pula
membiarkan Python tetap menjadi satu-satunya backend tanpa alasan.
Pilih boundary yang jelas dan ukur.

3.2 Implementasi teknis Rust
- Buat workspace Cargo yang terstruktur dan dapat dibangun.
- Buat crate library Rust dengan API stabil.
- Gunakan PyO3/maturin untuk binding Python jika kompatibel dengan target.
  Jika target Android/Termux tidak mendukung toolchain tertentu, evaluasi
  alternatif FFI/CLI/library dan dokumentasikan alasan teknis.
- Buat wrapper Python dengan feature detection dan fallback yang transparan.
- Jangan mengklaim Rust aktif bila modul native tidak berhasil dimuat.
- Buat parity test Python vs Rust untuk semua fungsi yang dipindahkan.
- Output harus identik atau memiliki toleransi numerik yang ditentukan.
- Tambahkan fuzz/property tests untuk parser, normalizer, dedup dan scoring.
- Tambahkan benchmark Python vs Rust dengan dataset representatif.
- Jangan mengaktifkan Rust hanya karena lebih cepat pada microbenchmark;
  ukur end-to-end latency, throughput, memory, startup, dan biaya kompleksitas.
- Rust build gagal tidak boleh membuat sistem kehilangan data atau
  menghasilkan output yang diam-diam berbeda.
- Catat backend yang digunakan per operasi dan fallback reason.

3.3 Definition of Done Rust
- Cargo build/test lulus.
- Python extension berhasil diimpor pada target yang dinyatakan didukung.
- Parity suite lulus.
- Benchmark dapat direproduksi.
- Fallback Python diuji.
- Status `rust_active`, `python_fallback`, `unavailable` ditampilkan jujur.
- Tidak ada placeholder `NOT_IMPLEMENTED` untuk scope Rust yang dijanjikan.

- entity extraction;
- prospect research synthesis;
- lead qualification;
- conversation response;
- objection handling;

- Pisahkan system instruction dari konten eksternal.
- Jangan masukkan API key, credential, private customer data, atau data
  sensitif yang tidak dibutuhkan ke prompt.
- Tambahkan grounded response: klaim harus menunjuk catalog/evidence/quote.
- Confidence rendah atau konflik data → bertanya, menahan klaim, atau handover.
- Evaluasi kualitas model per tugas, bukan hanya jawaban terlihat bagus.

ANALYST:

CLOSER:

- Menyimpan ringkasan memori dengan provenance dan correction handling.

GUARDIAN:
- Deterministic policy enforcement dan veto.
- Consent, lawful basis, suppression, opt-out, contact lock, rate limit,

- Memeriksa setiap outbound message dan tool action.
- Tidak dapat di-bypass oleh LLM, admin biasa, agent lain, retry, atau fallback.

5.2 Sumber data dan konektor
Buat connector interface dan implementasi yang legal/official jika tersedia:
- Google Places API / Google Maps Platform sesuai ketentuan resmi.

- Data yang diberikan operator/import CSV.
- Sumber lain hanya setelah legalitas, terms, dan aksesnya diperiksa.

DILARANG:
- Mengakali login, CAPTCHA, paywall, rate limit, atau access control.

- mobile viewport/responsive hints;
- presence of product catalog/cart/checkout;
- contact/business identity;
- booking/order flow;

- broken links/basic accessibility signals;
- CTA, product pages, payment/delivery information;
- technology hints hanya jika dapat dideteksi dengan wajar.
Jangan melakukan vulnerability scanning agresif atau penetration test tanpa izin.
Jangan mengirim form, order, atau transaksi saat discovery.

5.4 Lead evidence
Setiap fakta harus memiliki:
source_id, source_url/reference, observed_at, evidence_type,
raw_excerpt/hash bila aman, confidence, freshness, verification_status.
Pisahkan OBSERVED, INFERRED, UNKNOWN, CONFLICTED, STALE.
Jangan mengubah inferensi menjadi fakta.
Jangan menyimpan data berlebihan.

5.5 Discovery query engine
- Query planner berdasarkan kota/area, vertical penjual produk, sinyal kebutuhan E-commerce/POS, dan produk yang relevan.
- Query expansion dan synonym dictionary Bahasa Indonesia.
- Coverage tracking dan dedup lintas sumber.
- Resume job dan checkpoint.
- Per-source quota dan fairness.
- Stop condition agar tidak melakukan pencarian tanpa batas.
- Operator dapat memasukkan target industri/wilayah, bukan harus mengedit kode.
- Hindari mengklaim "siapa pun yang membutuhkan" dapat ditemukan secara sempurna.
  Tujuannya memaksimalkan coverage sumber yang sah dan mengukur blind spot.

======================================================================
6. ANALYST: QUALIFICATION DAN PRIORITAS
======================================================================

Buat model penilaian yang explainable dan configurable. Pisahkan:
A. Product fit:
- E-commerce / toko online fit.
- POS / sistem kasir fit.
- Combined E-commerce + POS fit.
Business website fit dan web development umum bukan kategori produk
penjualan dan tidak boleh mendapat product-fit score tersendiri.
B. Need strength:
- pain point yang terbukti;
- proses manual;
- kompleksitas katalog/order;
- jumlah cabang bila tersedia;
- sinyal ekspansi;
- masalah UX/website yang teramati;
- relevansi solusi.
C. Buying readiness:
- minat eksplisit;
- waktu kebutuhan;
- decision-maker evidence;
- permintaan demo/penawaran;
- budget hanya jika disampaikan atau tersedia secara sah.
D. Evidence confidence:
- sumber independen;
- freshness;
- direct vs inferred;
- conflict.
E. Contact eligibility:
- consent, lawful basis, channel policy, suppression, opt-out.
Contact eligibility bukan skor probabilitas dan tidak dapat di-override oleh nilai
lead yang tinggi.

Output:
- score per product;
- overall priority;
- confidence;
- rationale;
- supporting evidence;
- missing information;
- disqualification reason;
- next-best-action;
- review_required.
Rubrik dan bobot harus dapat dikonfigurasi, diberi versi, dan diuji. Jangan
menganggap bobot awal proyek sebagai kebenaran ilmiah. Kalibrasikan dengan
data hasil penjualan nyata dan hindari bias kategori/ukuran bisnis.

7. CLOSER: AI SALES CONVERSATION YANG BENAR-BENAR BEKERJA
======================================================================

CLOSER harus berkembang dari draft-only menjadi conversation agent yang
dapat menjalankan percakapan nyata melalui channel connector yang sah.

7.1 Conversation engine
- Webhook inbound event dengan signature verification.
- Idempotency untuk mencegah pesan ganda.
- Ordering dan dedup event.
- Conversation ownership lock.
- Customer identity resolution dengan batas privasi.
- Context window management dan memory summarization.
- Per-customer CRM timeline.
- Intent/entity extraction.
- Language detection dan tone adaptation.
- Human handover.
- Delivery/read/reply status bila provider mendukung.
- Retry aman tanpa mengirim pesan ganda.
- Dead-letter queue dan replay yang diaudit.

7.2 Natural sales behavior
AI harus dapat:
- memperkenalkan solusi secara singkat dan relevan;
- menggali kondisi bisnis;
- memahami apakah pelanggan membutuhkan E-commerce/toko online, POS/kasir,
  atau kombinasi keduanya;
- bertanya satu pertanyaan paling penting per giliran;
- menyesuaikan penjelasan dengan industri pelanggan;
- memberi contoh alur kerja yang relevan;
- menjelaskan manfaat tanpa menjamin hasil finansial;
- membandingkan pilihan paket dari katalog;
- menjawab keberatan harga, waktu, kompleksitas, kepercayaan, migrasi,
  dukungan, integrasi, dan kesiapan tim;
- menawarkan demo;
- menyusun proposal dan quotation;
- melakukan negosiasi dalam rentang diskon dan syarat yang diizinkan;
- mencatat alasan kalah/menang;
- melakukan follow-up hanya bila memiliki dasar izin dan aturan kanal
  memperbolehkan;
- berhenti segera jika pelanggan menolak/opt-out.

7.3 Sales knowledge base
Buat sumber kebenaran terstruktur:
- product catalog;
- feature matrix;
- package/pricing;
- implementation timeline;
- onboarding process;
- support/SLA;
- integration compatibility;
- security/privacy statements;
- FAQ;
- case studies/testimonials yang terverifikasi;
- demo assets;
- terms and limitations.
Setiap item punya version, owner, last_verified_at, status, evidence.
AI dilarang mengarang jawaban jika knowledge base kosong. Jawab jujur,
ajukan klarifikasi, atau handover.

7.4 Objection playbook
Bangun playbook yang dapat dikonfigurasi dan dievaluasi untuk:
- "mahal";
- "saya sudah punya website/POS";
- "belum butuh";
- "takut sulit digunakan";
- "takut data hilang";
- "apakah bisa integrasi dengan ...?";
- "bisa bayar bertahap?";
- "saya perlu diskusi dengan partner";
- "kirim proposal dulu";
- "apa bedanya dengan kompetitor?";
- "berapa lama pengerjaannya?".
Jangan memaksa, menekan, memanipulasi, membuat scarcity palsu, atau
menggunakan dark patterns.

7.5 Pricing and negotiation
- Semua harga berasal dari katalog/quote engine yang disetujui pemilik.
- Harga final, diskon, pajak, biaya tambahan, masa berlaku, dan syarat
  harus dihitung deterministik.
- Batas diskon per role/agent.
- AI tidak boleh memberi diskon atau komitmen di luar kewenangannya.
- Untuk permintaan khusus, buat approval task atau handover.
- Quote memiliki ID, versi, expiry, itemized lines, currency, tax treatment,
  dan audit trail.

7.6 Deal and payment
- Status deal tidak boleh WON hanya karena pelanggan berkata "oke".
- Verifikasi pembayaran melalui payment provider/webhook resmi atau bukti
  yang diverifikasi manusia.
- Jangan menyimpan data kartu pembayaran.
- Idempotency dan reconciliation.
- Simpan bukti minimum yang diperlukan.
- Setelah deal valid, buat onboarding handoff dan task implementasi.

8. CHANNELS: INBOUND DAN OUTBOUND NYATA
======================================================================

Buat channel architecture modular:
- WhatsApp Business Platform / Cloud API resmi jika memenuhi syarat.
- Email melalui provider resmi (SMTP/API) dengan autentikasi yang benar.
- Website live chat/widget.
- Instagram/Messenger hanya melalui API dan permission resmi yang tersedia.
- Channel tambahan melalui connector contract.

Khusus WhatsApp:
- Gunakan WhatsApp Business Platform/Cloud API resmi.
- Implementasikan webhook verification, signature, message status, template
  messages, 24-hour customer service window, template category, opt-in,
  quality rating/rate limits sesuai dokumentasi terkini.
- Jangan menggunakan WhatsApp Web automation, browser bot, unofficial library,
  atau teknik yang menghindari aturan.
- Jangan mengirim cold message tanpa dasar izin yang sesuai.
- Inbound customer-initiated conversation dapat ditangani sesuai window
  dan policy resmi.
- Jika outbound business-initiated memerlukan template/opt-in, patuhi.
- Sediakan sandbox/test number bila tersedia.

Email:
- SPF/DKIM/DMARC guidance.
- Bounce, complaint, unsubscribe, suppression.
- Rate limit dan sender reputation.
- Tidak melakukan spam/bulk cold email yang melanggar hukum atau provider policy.

Website chat:
- Widget ringan, secure session, rate limiting, consent notice, privacy notice.
- Handover ke manusia.
- Tidak mengungkap data pelanggan lain.

Sender Gateway:
- Semua outbound wajib melewati satu jalur GUARDIAN authorize_send.
- Adapter hanya dapat diregistrasi bila official/approved.
- Default deny.
- Idempotency key per outbound.
- Delivery uncertain tidak boleh auto-resend tanpa reconciliation.
- Per-channel kill switch dan global kill switch.
- Per-customer contact lock dan suppression lintas kanal.
- Audit setiap keputusan allow/deny.
- Dry-run/sandbox/live mode yang jelas dan terpisah.

PENTING: Jangan mengaktifkan live outbound secara default. Implementasikan
fitur lengkap dan sandbox tests, tetapi konfigurasi awal tetap:
RESEARCH_ONLY=true
OUTBOUND_ENABLED=false
DRY_RUN=true
LIVE_SEND_APPROVED=false
GLOBAL_KILL_SWITCH=true
Sampai pemilik mengisi credential, menyelesaikan setup resmi, memastikan
consent dan kebijakan, dan secara eksplisit mengaktifkan kanal. Ini bukan
alasan untuk tidak membangun adapter; adapter dan seluruh tesnya tetap wajib.

9. GUARDIAN: GOVERNANCE, SECURITY, PRIVACY, DAN COMPLIANCE
======================================================================

Pertahankan prinsip default-deny dan tingkatkan:
- consent registry per channel, purpose, timestamp, source, scope, expiry;
- lawful-basis record sesuai yurisdiksi dan use case;
- suppression list lintas kanal;
- opt-out multilingual dan slang Bahasa Indonesia;
- opt-out precedence tertinggi;
- contact lock dan anti-duplicate;
- frequency cap dan quiet hours;
- channel-specific policy;
- content lint dan claim-evidence matching;
- approval hash dan tamper-evident audit;
- human override tidak dapat menembus hard legal/safety blocks;
- data retention policy;
- privacy export/delete workflow;
- access control roles;
- secret management;
- encryption at rest/in transit jika relevan;
- PII masking;
- prompt injection defense;
- SSRF defense;
- webhook signature verification;
- dependency scanning dan secure configuration;
- incident response dan backup/restore.

Patuhi hukum perlindungan data yang berlaku, termasuk UU Pelindungan Data
Pribadi Indonesia bila relevan, aturan anti-spam/komunikasi, ketentuan
platform, serta aturan yurisdiksi target pelanggan. Jangan memberi opini
hukum final; sediakan checklist compliance dan tandai kebutuhan review ahli.

Jangan mengumpulkan nomor telepon/email pribadi dari sumber yang tidak
mengizinkan penggunaan tersebut. Prioritaskan business contact yang
dipublikasikan untuk tujuan bisnis dan tetap periksa dasar kontak.
Jangan menghubungi orang hanya karena datanya ditemukan.

10A.6. CARA AGENT MENGGUNAKAN KATALOG

SCOUT:
- Menemukan prospek dan menyimpan evidence kebutuhan.
- Menggunakan kategori/vertical dan indikator kebutuhan dari katalog
  untuk membantu query planning.
- Tidak boleh mengirim penawaran dan tidak boleh mengarang bahwa bisnis
  membutuhkan jasa tertentu.

ANALYST:
- Membandingkan kebutuhan prospek dengan setiap jasa/paket published.
- Menghasilkan product-fit score per jasa beserta evidence, confidence,
  alasan cocok/tidak cocok, gap, dan pertanyaan discovery.
- Mengabaikan produk draft, archived, stale, atau unavailable.
- Tidak menjadikan harga murah sebagai satu-satunya alasan kecocokan.

CLOSER:
- Mengambil informasi hanya dari katalog/knowledge center versi aktif.
- Menjelaskan manfaat sesuai masalah yang telah dikonfirmasi.
- Mengajukan pertanyaan discovery jika data kebutuhan belum cukup.
- Menawarkan maksimal opsi yang relevan, bukan membanjiri calon pelanggan.
- Menjawab harga sesuai pricing_model.
- Membuat quote hanya melalui quote engine.
- Tidak menjanjikan fitur, timeline, diskon, hasil bisnis, atau SLA
  di luar data dan kewenangannya.
- Jika jawaban tidak ada di knowledge center, menyatakan belum memiliki
  informasi terverifikasi dan menawarkan handover.

GUARDIAN:
- Memvalidasi status publish, freshness, harga, diskon, klaim, bukti,
  izin penggunaan portofolio/testimoni, serta kewenangan agent.
- Memblokir penawaran dari produk draft/archived/stale.
- Memblokir diskon di luar batas.
- Memblokir klaim yang tidak punya evidence.
- Mencatat versi katalog dan knowledge base yang dipakai pada setiap
  percakapan, quote, dan proposal.

10A.7. PRICING ENGINE DAN QUOTE GENERATOR

Dukung tiga mode utama:
A. Fixed price: AI hanya menyampaikan harga yang ditetapkan.
B. Flexible within limits: AI dapat menyusun penawaran dalam rentang
   harga/diskon yang disetujui admin, dengan perhitungan transparan.
C. Custom quote after discovery: AI mengumpulkan kebutuhan dan membuat
   draft perhitungan; quote final harus mengikuti otorisasi yang ditetapkan.

Pilihan awal konfigurasi yang disarankan: flexible within limits.
Pilihan ini bukan harga otomatis dan tidak boleh membuat angka sendiri.
Jika admin belum memasukkan nilai batas harga/diskon, fleksibilitas
dinonaktifkan sampai aturan lengkap.

Quote engine wajib:
- menghitung subtotal, add-on, biaya setup, recurring fee, pajak/biaya,
  diskon, total, termin, dan masa berlaku;
- menyimpan input dan rumus perhitungan;
- mendukung versi quote dan revisi;
- mencatat siapa/agent yang membuat dan menyetujui;
- mencegah diskon bertumpuk yang melampaui batas;
- mengunci snapshot harga dan spesifikasi pada saat quote diterbitkan;
- menandai quote kedaluwarsa;
- tidak mengubah quote lama saat katalog berubah;
- mengharuskan handover jika harga custom memerlukan keputusan manusia.

10A.8. STATUS, PUBLIKASI, DAN PERUBAHAN KATALOG

Ketentuan:

- perubahan besar pada harga/fitur membuat versi baru;
- quote yang sudah diterbitkan tetap memakai snapshot versi lama;
- perubahan katalog tidak boleh mengubah isi proposal historis;
- data yang melewati stale_after ditandai stale dan tidak boleh dipakai
  untuk klaim sensitif sampai diverifikasi ulang;
- setiap perubahan masuk audit log;
- sediakan preview sebelum publish dan rollback ke versi terdahulu;
- admin dapat menonaktifkan jasa segera jika ada kesalahan.

   atau pemesanan E-commerce yang sesuai katalog.
G. Bisnis sudah memiliki E-commerce/POS yang memadai → jangan dipaksa membeli.
H. Bisnis tidak menjual produk atau tidak memiliki kebutuhan E-commerce/POS
   yang dapat dibuktikan → NOT_A_FIT, bukan lead berkualitas.
H. Prospek tidak memiliki kebutuhan yang jelas → nurture/unknown, bukan false claim.
I. Pelanggan bertanya harga → jawab dari katalog.

P. Rust unavailable → Python fallback terlihat.
Q. Customer asks feature unavailable → AI menjawab jujur.
R. Payment unverified → deal bukan WON.
S. Prompt injection dalam website/pesan → tidak mengubah policy.

Gunakan command yang konsisten dan dokumentasikan help aktual.

======================================================================
19. DEFINITION OF DONE GLOBAL
======================================================================

Proyek hanya boleh dinyatakan UPGRADED bila:

1. Fitur lama tetap bekerja atau perubahan breaking dijelaskan dan dimigrasikan.
2. Rust benar-benar dibangun, dipanggil dari Python untuk scope yang dipilih,
   parity-tested, benchmarked, dan fallback terlihat.
3. Gemini/Ollama memiliki integrasi implementasi nyata dan status verifikasi
   yang jujur.
4. SCOUT mendukung vertical bisnis penjual produk yang relevan untuk E-commerce/POS, bukan pencarian umum semua jenis usaha.
5. Ada connector source nyata yang sah dan dapat diverifikasi; connector lain
   yang memerlukan akses khusus diberi status NOT_CONFIGURED/NOT_VERIFIED.
6. ANALYST dapat menilai kebutuhan website/e-commerce/POS secara terpisah
   dan menjelaskan bukti.
7. CLOSER mampu multi-turn conversation menggunakan LLM dan knowledge base,
   bukan hanya draft deterministik.
8. Inbound channel nyata/sandbox berjalan dengan webhook dan idempotency.
9. Outbound adapter resmi tersedia dan melewati GUARDIAN authorize_send.
10. Consent, opt-out, contact lock, kill switch, rate limits, dan audit tidak
    dapat dilewati.
11. CRM dan dashboard tersedia serta responsif.
12. Quote, proposal, deal, payment verification, dan onboarding workflow ada.
13. Privacy export/delete dan retention berjalan serta diuji.
14. Semua unit/integration/e2e/adversarial tests dilaporkan.
15. Tidak ada klaim fitur, harga, konektor, atau status yang palsu.
16. Setup dan deployment terdokumentasi.
17. Semua known gaps ditampilkan dalam PRODUCTION_READINESS.md.

Jika satu syarat eksternal terhalang oleh credential, akses, biaya, approval,
atau policy pihak ketiga, jangan menyembunyikannya. Selesaikan implementasi
yang dapat dilakukan, sediakan sandbox, tulis langkah konfigurasi, dan
tandai status yang benar. Tidak boleh memalsukan live verification.

20. ATURAN KERJA ENGINEERING
======================================================================

- Baca file sebelum mengedit.
- Gunakan patch kecil dan terarah; hindari rewrite massal tanpa alasan.
- Pertahankan API dan schema yang masih digunakan.
- Tambahkan migration, bukan edit database pengguna secara manual.
- Setiap fitur baru harus punya test.
- Jalankan test relevan setelah setiap perubahan besar.
- Jalankan full test suite pada akhir setiap phase.
- Periksa lint/type/security bila tool tersedia.
- Jangan menurunkan kualitas test untuk mendapatkan hasil hijau.
- Jangan hardcode API key, model, URL, harga, atau credential.
- Jangan menambahkan dependensi tanpa mengevaluasi ukuran, lisensi,
  keamanan, platform support, dan biaya.
- Catat keputusan arsitektur.
- Hindari TODO kosong, pass placeholder, fake adapter, dan mock yang
  disamarkan sebagai integrasi nyata.
- Jika fitur belum dapat diselesaikan, buat error/status eksplisit dan
  dokumentasikan blocker.
- Jangan menghapus data pengguna.
- Jangan menjalankan outbound live send, mengirim email/WhatsApp sungguhan,
  membuat transaksi, atau menghubungi prospek selama build/test.
- Gunakan fixture, mock, local test server, dan sandbox resmi.
- Semua live actions tetap disabled setelah upgrade sampai pemilik
  melakukan konfigurasi dan aktivasi eksplisit per kanal.
- Jangan meminta user melakukan pekerjaan coding manual jika agent dapat
  mengerjakannya di workspace. Untuk credential/akun/legal setup yang memang
  hanya dapat dilakukan pemilik, berikan instruksi langkah demi langkah.
